# Intake Failure Recovery Matrix — Program Intake Sprint 001 (2026-08-04)

Phase 4 requirement: simulate each failure scenario against all 3 pipelines; the document must remain
reconstructible. ✅ = recoverable / no loss. ⚠️ = degraded but not lost / honest partial state. ❌ = defect
(fixed this sprint unless noted).

| Scenario | Pipeline A | Pipeline B (worker) | Pipeline C (finalize) |
|---|---|---|---|
| Upload interrupted mid-request | ✅ Nothing committed, client retries, clean | ✅ Storage upload is a separate step from `intake_jobs` insert — worst case is an orphaned blob (`INTAKE-002`, deferred), never a lost *tracked* job | ✅ Same as A — nothing committed until each step completes |
| OCR crash/exception | ✅ Caught, HTTP 422/500 to caller, no partial DB row | ✅ Fail-soft by design (`ENGINEERING_PRINCIPLES.md`) — scanned/unreadable saved as `document_type='other'`, confidence=0, routed to review queue, job completes normally (not a retry loop, since OCR failure isn't transient) | ✅ Caught by outer try/except, `doc_linked=False`, honest |
| Storage upload crash/timeout | ✅ **Fixed this sprint** — best-effort, non-blocking, falls back to old label, request still succeeds | ✅ N/A at this stage (Storage write happens at the earlier upload endpoint, not inside the worker) | N/A (reads pre-existing Storage object) |
| Storage succeeds, subsequent step fails | ⚠️ N/A (Storage write is now the earliest step on the happy path; a later Pinecone/DB failure doesn't undo it — original file remains safely stored even if indexing fails) | ❌ **Orphaned blob if `enqueue_intake_job` RPC fails after Storage upload succeeds** — no `intake_jobs` row ever created to reference it, no cleanup job/lifecycle policy exists. Deferred, `INTAKE-002` | N/A |
| Worker restart mid-job | ✅ N/A (synchronous, no persistent worker) | ✅ Stale-job reaper (`reap_stale_jobs`) reclaims jobs past `stale_after_s`; **the false-success bug this sprint fixed was exactly the dangerous variant of this scenario** — a crash after `create_document()` but before `write_processing_outcome()` now correctly triggers clean-slate reprocessing instead of a silent false-complete | N/A (synchronous) |
| Full process restart | ✅ N/A | ✅ Same reaper mechanism; job durability lives in `intake_jobs`, not in-process memory | N/A |
| DB insert fails after Pinecone succeeds (ghost vector) | ✅ Project Sentinel's existing hard-fail (HTTP 500, `api.py:4243-4247`) — an honest total failure, no ghost state silently reported as success | N/A (no Pinecone write in the worker path — that only happens at Pipeline A/C) | ❌ **Not hard-failed** — `doc_linked=False` is honest, but the overall response still says `"ok": true"` since the `predmet` (case) row was already created earlier in the same call. Deferred with reasoning, `INTAKE-001` (a Sentinel-style hard-fail here risks misreporting a genuinely-created case as a total failure and inviting a duplicate-creating retry — needs a real partial-success response design, not a blind port) |
| Pinecone quota/429 | ✅ `pinecone_ok=False`, `status="sacuvano"` (not `"indeksirano"`), document still saved, honest | N/A (Pinecone write happens outside the worker) | ✅ Same `pinecone_ok` fallback pattern as A |
| Network timeout (RAG/downstream) | ✅ Caught, logged, flow continues without RAG context (auto-procena degrades gracefully, not blocked) | N/A | ✅ Same |
| Disk full (tempfile write) | ✅ `tempfile.NamedTemporaryFile` failure propagates as a caught exception → clean error response | ✅ Same tempfile pattern inside `_process()`, `finally` block always attempts cleanup | ✅ Same pattern |
| Retry after partial completion (the sprint's central regression) | N/A | ✅ **Fixed** — see "worker restart" row above; regression-tested in `tests/test_intake_worker_phase1a.py::test_process_partial_document_without_outcome_is_deleted_and_reprocessed` | N/A |
| Duplicate upload (same file twice) | ⚠️ Two independent `predmet_dokumenti` rows — by design, no dedup logic exists on this pipeline (each call is an explicit user action, "upload this file to this case," not a background dedup problem) | ✅ `intake_jobs` has a `dedup_check` status stage (migration 073) — Pipeline B has real dedup infrastructure Pipeline A doesn't | N/A (finalize is 1:1 with its own job) |
| Parallel upload / race condition | ✅ Each request is independent, no shared mutable state at the DB-write level (`redni_broj` computation has a benign best-effort race — a duplicate `redni_broj` is a display-ordering cosmetic issue, not data loss) | ✅ `claim_next_job`'s `SELECT...FOR UPDATE SKIP LOCKED` is atomic — two workers cannot claim the same job (this is exactly why migration 091's *absence* matters for the separate Event Bus outbox, a different table with a weaker claim mechanism) | N/A |
| Rollback (mid-transaction abort) | ✅ No multi-statement transaction exists — each `INSERT`/`UPDATE` is independently committed, so there is no partial-transaction state to roll back from; failure at any step just means later steps didn't run | ✅ Same — `_process()`'s steps are independent writes, which is exactly why the false-success bug (a *sequence* of writes not all completing) was possible and needed the explicit completion-signal fix rather than relying on transactional atomicity | ✅ Same |
| Power failure / abrupt kill | ✅ In-flight request is simply lost, client sees a connection error, no ambiguous state persists | ✅ Job remains in `preprocessing` status, reaper reclaims it after `stale_after_s`, then the false-success fix ensures correct reprocessing rather than false-complete | ✅ Same as A |

**Summary**: 2 real gaps remain, both deferred with explicit reasoning rather than blind-fixed:
`INTAKE-001` (Pipeline C's ghost-vector-on-total-insert-failure) and `INTAKE-002` (orphaned Storage blobs on
Pipeline B enqueue failure). Neither causes *tracked* document loss — `INTAKE-001` produces an honest
`dokument_povezan: false` signal (frontend surfacing not verified, backend is honest); `INTAKE-002` wastes
Storage space on bytes that were never referenced by any job a user could see. The sprint's single most
dangerous scenario — silent false-success on worker crash-retry — is fixed and regression-tested.
